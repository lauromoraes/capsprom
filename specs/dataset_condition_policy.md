# Dataset Condition Policy

This policy defines the two data conditions under which CapsProm evaluates
models, the three kinds of data intervention that separate them, and the
records each derived dataset must carry. It refines
`specs/data_provenance_policy.md` §4 and generalizes the decision already
taken for GraphPro in `specs/graphpro_dataset_reconstruction.md`.

Status: design. No dataset has yet been built under this policy, and no
existing build, partition, or execution gate changes because of it.

## 1. Conditions

| Condition | Code | Inputs | Purpose |
| --- | --- | --- | --- |
| Released, filtered | `orig` | Canonical collections of `source_acquisition_v1`, unchanged in sequence and label | Reproduce the source study's baselines; evaluate models on the data the study distributed |
| Reconstructed | `recon` | Verified references: assemblies, dated TSS annotations, primary coordinate tables, and a declared negative-construction rule | Evaluate models on data whose biological identity is established independently of the released files |

The two conditions are complementary, not alternatives. An `orig` dataset
answers "what does the released benchmark support?"; a `recon` dataset answers
"what holds when the examples are rebuilt from verified references?". Neither
replaces the other, and their results are never pooled.

## 2. Interventions

Every change between an acquired file and an experimental dataset is one of
the following. The test is applied per change, in this order; the first that
matches decides.

1. **Reconstruction.** Any change that makes a dataset row depend on data other
   than its acquired record: re-extraction or extension of a window from a
   genome, re-centring on an externally verified TSS, a new label, a new
   positive taken from a reference, or a negative not generated by the
   published procedure from released positives. A dataset containing any such
   row is `recon`.
2. **Metadata correction.** A change to descriptive fields only (organism,
   assembly, accession, strand annotation, coordinate convention) that leaves
   the set of rows, every sequence, and every label unchanged, and that is
   supported by a recorded finding of status Fact. The original value is kept
   beside the corrected one (§4); it is never overwritten.
3. **Filtering.** Removal of whole records by a rule declared before the
   dataset is built. Each retained record is identical in sequence, label, and
   source class to an acquired record, and each removal is counted by rule.

Two further operations do not change the condition, provided they are declared
in the protocol and applied to every record alike:

- **Protocol transformation**: a deterministic function of the released
  sequence alone, such as cropping at a documented index or encoding. If the
  index itself is not documented by the source and has to be verified against a
  reference, the crop is still a protocol transformation, but the dataset's
  comparability is at most `qualified` (§5) until the index is verified.
- **Published negative generation**: negatives produced from released
  positives by the source study's own documented procedure (for example
  Bhandari block shuffling). Such negatives are procedurally, not
  byte-for-byte, reproduced when the seed is unknown, and that is recorded.

A change that cannot be placed in one of these classes is treated as
reconstruction. A dataset is labelled `orig` only if every row resolves to an
acquired `record_id` through filtering, a protocol transformation, or the
published negative procedure. Any other row makes it `recon`; a modified
version is never labelled as original by default.

Examples:

| Change | Class |
| --- | --- |
| Drop the 38 Bhandari windows shorter than 1,000 nt | Filtering |
| Drop CDBProm 99-nt negatives | Filtering |
| Remove exact within-class duplicates, keeping the first by `record_id` | Filtering |
| Record that `bhandari-nominal-plant` is *Mus musculus* `mm10` | Metadata correction |
| Re-extract truncated Bhandari windows from the full assembly | Reconstruction |
| Recreate Bhandari positives from `mm10` coordinates (sequence-identical) | Reconstruction (the rows now come from the genome; identity to the release is a verification result) |
| GraphPro positives from Promotech and primary TSS tables | Reconstruction |
| GC-matched genomic negatives | Reconstruction |
| Crop the 1,000-nt Bhandari window to the eukaryotic window (−200..+50, indexes 500..750) of `specs/sequence_window_policy.md` | Protocol transformation |

## 3. Protocols inside the `orig` condition

| Protocol | Code | Definition | Allowed use |
| --- | --- | --- | --- |
| Published | `pub` | The source study's own split, window, negative procedure, subsampling, and metrics, as far as they are documented | Reproduction of the study's reported baselines |
| Common | `common` | The project protocol: `configs/evaluation_protocol_v3.yaml` (or its successor), group-safe partitions, the domain windows of `specs/sequence_window_policy.md`, project negative policy | Model comparison across sources under one protocol |

A `pub` result is compared with the published number; a `common` result is
compared with other `common` results. A `common` result is never presented as a
reproduction of a published one.

Where the study leaves a step undocumented (seed, shuffling block size,
subsampling), the `pub` protocol fixes the missing value before execution,
records it as an assumption with its source (for example a repository file),
and states that the reproduction is procedural.

## 4. Identifiers and versions

- Canonical collection IDs (`bhandari-nominal-plant`, `graphpro-ecol`, …) are
  historical identifiers of acquired files. They are never renamed.
- Derived datasets use
  `<collection_id>.orig-<protocol>-v<N>` for the released condition and
  `<source>-<organism_slug>-reconstructed-v<N>` for the reconstructed one,
  matching the existing `graphpro-reconstructed-v1`. The two never share an
  identifier, a config, a state path, or an output directory.
- Every derived dataset records, per organism:
  - `source_designation`: the name used by the release or publication, verbatim
    (for example `Plant_promoters`, "A. thaliana");
  - `verified_organism` and `verified_assembly`, with the IDs of the findings
    that establish them, or `unverified`;
  - `designation_conflict`: `none`, or the finding IDs of a conflict.
  Results tables show the verified organism and, where they differ, the
  source designation in a separate column.
- A new filter rule, correction, reference, seed, or protocol creates a new
  version; earlier versions stay readable.

## 5. Ledger and comparability

Each build writes a ledger next to its manifest, with:

- input collection IDs and the canonical manifest SHA-256;
- one entry per intervention: class (§2), rule ID, justification with finding
  IDs, records before and after per class, excluded `record_id`s or their
  hash;
- for each partition: rows per class before and after each filter, so the
  effect of a filter on train, validation, and test is visible;
- for `recon`: reference files and their digests, the reconstruction rule, and
  a per-record comparison with the released record (identical, changed,
  added, not released);
- a `comparability` value for the published results:

| Value | Meaning |
| --- | --- |
| `direct` | `pub` protocol on released data, filtered only as the publication itself describes |
| `qualified` | `pub` protocol, with filters or assumed parameters the publication does not describe; the ledger quantifies the difference |
| `not_comparable` | the data or protocol differ in a way that invalidates the published number as a reference: another organism, another task, or a different split design. The reason is stated. |

`common` and `recon` results are `not_comparable` to published numbers by
definition, and are reported as such.

## 6. Traceability across conditions

The same acquired record may appear in both conditions. The ledgers make this
visible through `record_id` (released) and the reference locus (reconstructed),
so that the effect of each intervention can be measured on matched records:
released versus filtered (effect of filtering), filtered versus reconstructed
on the records present in both (effect of reconstruction), and reconstructed
records absent from the release.
